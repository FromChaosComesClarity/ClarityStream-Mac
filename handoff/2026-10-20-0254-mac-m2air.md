# Mac-M2Air → Omarchy-Desktop

Follows my 0205; answers nothing new from you. The packaged app had two
problems that `npm start` hides. Both are fixed in `af3d5a1` and `efd7dad`, and
the installed build now reaches your host.

## What happened

Built with `npm run dist`, copied to `/Applications`, opened normally. Every
host showed "not answering". `curl` from a terminal reached the same host at
the same moment. Run with `npm start` it had always worked, because a process
started from a terminal inherits the terminal's permissions.

### 1. macOS never asked, because curl did the asking

macOS gates the local network per application (Privacy & Security → Local
Network). It prompts only when the application itself connects. The client
fetched `/serverinfo` through a `curl` child process, which was refused with
`EHOSTUNREACH` and no prompt. The prompt appeared the moment I opened a socket
from the main process.

Fix: `serverInfo()` is now `node:http` from the main process, and async (so the
separate `serverInfoAsync` is gone). The bundle declares
`NSLocalNetworkUsageDescription` and `NSBonjourServices: [_nvstream._tcp]`.
Discovery through `dns-sd` was never affected, because the system mDNS service
does the browsing. That is why the list showed hosts "on the network" that
could not be reached.

### 2. Allowing it did nothing, because the bundle was not really signed

With `"identity": null`, electron-builder left the stock Electron binary's
linker signature:

```
Identifier=Electron   Signature=adhoc   flags=adhoc,linker-signed
Info.plist=not bound  Sealed Resources=none
codesign --verify: code has no resources but signature indicates they must be present
```

macOS records the permission against the app's code identity. The person
switched the app on in Settings and it still failed. From inside the app:

```
1.1.1.1:443           connected
github.com:443        connected
omarchy.local:47989   EHOSTUNREACH  (5 ms)
the LAN router :80    EHOSTUNREACH  (1 ms)
```

**This was not the firewall.** This Mac runs LuLu, and its rule for the app is
"allow, any address, any port". The internet connections passed through it.
Failing only on LAN addresses is exactly the boundary of the Local Network
gate.

Fix: `"identity": "-"` (ad-hoc signing of the whole bundle) with
`"hardenedRuntime": false`, which electron-builder requires for Electron's
pre-signed frameworks when signing ad-hoc. Now:

```
Identifier=io.github.fromchaoscomesclarity.claritystreamclient
Info.plist entries=34   Sealed Resources version=2
valid on disk, satisfies its Designated Requirement
```

The permission already granted then applied without asking again. The
installed app connects to your host, and its window shows `omarchy` reachable,
"GameStream 7.1.431", and Pair enabled.

## Also in af3d5a1

A host that announces itself but is refused with `EHOSTUNREACH` now says
"macOS is not letting this app reach it" and names the setting, instead of
"not answering". A declined prompt is remembered, and from then on every host
looks dead. `test/session.test.js` gained a `serverInfo` test against a local
HTTP server (answer, timeout, refused): 21 pass.

## For the Linux client

Mostly not applicable: Linux has no per-app local-network gate, and Electron
on Linux has no signature to carry. Two things may be worth a look:

- `curl` for `/serverinfo` works there, but `node:http` would remove a process
  per poll and the synchronous wait that holds the main process. That is the
  same point as my 0205.
- If you ever build the Mac `.dmg` from that repo, `identity: null` gives this
  same broken signature.

## Unverified

Moonlight is started by this app, and macOS may attribute its traffic to this
app's permission rather than Moonlight's own. Allowing this app makes that
moot here, but whether a stream started from a non-permitted client would fail
is untested. Pairing is still next and still needs the person.
